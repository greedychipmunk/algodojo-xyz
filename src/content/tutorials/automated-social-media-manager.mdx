## What You're Building

Running a brand's social presence is mostly the same loop, over and over: check what people said to you, decide what's worth a response, reply in a consistent voice, and every so often publish something longer. It's repetitive, it's easy to fall behind on, and the tone drifts whenever a different person picks it up.

That loop is a perfect fit for a **stateful agent**. In this tutorial you'll build a social media manager that runs on its own:

- It pulls your **Bluesky** mentions with the [social-cli](https://github.com/letta-ai/social-cli).
- A **Letta** agent reads each mention, decides whether it deserves a reply, and drafts one in a brand voice it holds in persistent memory.
- A local driver posts the agent's decisions back to Bluesky.
- On a daily schedule, the agent writes a long-form digest and publishes it to **Leaflet** (long-form publishing on the AT Protocol).

If you've worked through [Build Your First Letta Agent](/tutorials/letta-build-your-first-agent) and [Give Your Letta Agent Custom Tools](/tutorials/letta-agent-tools), you have everything you need. We'll lean on the same patterns — persistent [memory blocks](/tutorials/letta-memory-blocks) for the brand voice, custom tools for structured decisions — and connect them to a real social account.

## The Architecture (and one important constraint)

Before any code, understand the shape of the system, because one detail drives every design decision that follows.

Letta executes custom tools in a **sandbox on the Letta server**, not on your laptop. As you saw in the custom-tools tutorial, every `import` has to live *inside* the tool body because the function runs in an isolated environment. That sandbox does **not** have the `social-cli` binary installed, and it does **not** have your Bluesky credentials.

So we deliberately split responsibilities:

- **The Letta agent is the brain.** It holds the brand voice in memory and makes decisions. Its tools are tiny, dependency-free functions that just *record* a decision (the reply text, or a "skip"). Those are safe to run in the sandbox.
- **A local Python driver is the hands.** It runs `social-cli` on your machine — where the binary and credentials live — to fetch mentions and execute the agent's decisions.

This is exactly how the official [example-social-agent](https://github.com/letta-ai/example-social-agent) is structured, and it keeps your credentials off the Letta server entirely.

```text
 social-cli sync ─▶ inbox-bsky.yaml ─▶ driver ─▶ Letta agent (decides)
                                                       │
                          driver ◀── draft_reply/skip ─┘
                            │
                            ▼
                 social-cli reply / post / publish ─▶ Bluesky + Leaflet
```

## Project Folder Structure

Create a project directory with this layout. We'll fill in each file as we go.

```text
social-manager/
├── .env                  # Bluesky + Leaflet credentials, Letta config
├── config.yaml           # social-cli account configuration
├── requirements.txt      # Python deps for the driver
├── tools/
│   └── decisions.py      # the agent's decision tools (sandbox-safe)
├── create_agent.py       # one-time setup: register tools, create the agent
├── manager.py            # the recurring driver (engage / post / publish)
├── state/                # social-cli writes inbox-*.yaml here
└── content/
    └── digests/          # archive of published Leaflet articles
```

Create the scaffolding now:

```bash
mkdir -p social-manager/{tools,state,content/digests}
cd social-manager
```

## Step 1 — Install and Build social-cli

`social-cli` is a Node tool. You'll need Node 18+ and `pnpm`. Clone, build, and link it so the `social-cli` command is available globally:

```bash
git clone https://github.com/letta-ai/social-cli.git ~/social-cli
cd ~/social-cli
pnpm install
pnpm build
pnpm link --global      # exposes `social-cli` on your PATH
```

Confirm it's reachable from anywhere:

```bash
social-cli --help
```

If you'd rather not link globally, you can run it from the repo with `pnpm social-cli ...` — but the rest of this tutorial assumes the global `social-cli` command. Head back to your project directory:

```bash
cd ~/social-manager
```

## Step 2 — Create a Bluesky App Password

Never put your real Bluesky password in a config file. Bluesky issues scoped **app passwords** for exactly this.

1. In the Bluesky app or on [bsky.app](https://bsky.app), go to **Settings → Privacy and Security → App Passwords**.
2. Click **Add App Password**, give it a name like `social-manager`, and create it.
3. Copy the generated code — it looks like `xxxx-xxxx-xxxx-xxxx`. You won't be able to see it again.

## Step 3 — Set Up a Leaflet Publication

[Leaflet](https://leaflet.pub) is a long-form publishing tool built on the AT Protocol, so it uses the **same Bluesky identity** — no separate account.

1. Go to [leaflet.pub](https://leaflet.pub) and sign in with your Bluesky handle.
2. Create a new **publication** (this is the "blog" your digests belong to).
3. Open the publication's settings and copy its **AT-URI**. It looks like:

   ```text
   at://did:plc:abcd1234.../site.standard.publication/xyz789
   ```

That URI is how `social-cli` knows where to publish. Keep it handy for the next step.

## Step 4 — Configure social-cli

Two files configure the CLI: `config.yaml` lists your accounts and points to the credentials file, and `.env` holds the secrets.

Create `config.yaml`:

```yaml
accounts:
  bsky:
    handle: your-handle.bsky.social
    credentials: .env
state:
  stateDir: ./state
```

Create `.env` with your real values:

```text
# Bluesky (AT Protocol)
ATPROTO_HANDLE=your-handle.bsky.social
ATPROTO_APP_PASSWORD=xxxx-xxxx-xxxx-xxxx
ATPROTO_PDS=https://bsky.social

# Leaflet long-form publishing
LEAFLET_PUBLICATION_URI=at://did:plc:abcd1234.../site.standard.publication/xyz789

# Letta server + the agent we'll create in Step 7
LETTA_BASE_URL=http://localhost:8283
MANAGER_AGENT_ID=
```

Add `.env` to your `.gitignore` immediately — it contains live credentials:

```bash
echo ".env" >> .gitignore
```

The `state.stateDir: ./state` line tells `social-cli` to write its inbox files into the project's `state/` folder instead of a hidden global directory, so you can inspect them easily.

## Step 5 — Smoke-Test social-cli

Before involving any AI, prove the CLI can authenticate and act. Run these from the project root so it picks up `config.yaml`:

```bash
social-cli whoami                     # should print your handle + DID
social-cli post "Hello from social-cli 👋" -p bsky
```

Check your Bluesky profile — the post should be live. Now test long-form publishing without actually publishing, using `--dry-run`:

```bash
social-cli publish --title "Dry run" --content "# Testing\nJust checking the pipeline." --dry-run
```

If `whoami` works and the dry run reports the record it *would* create, your credentials and Leaflet publication are wired correctly. Delete the test post when you're done:

```bash
social-cli feed -p bsky -n 1          # find your post's at:// URI
social-cli delete <at-uri> -p bsky
```

## Step 6 — Start a Letta Server

The agent needs a running Letta server. If you don't already have one, Docker gets you there in under a minute:

```bash
docker run -d --name letta-server \
  -p 8283:8283 \
  -e OPENAI_API_KEY="your-openai-key" \
  letta/letta:latest
```

This matches the setup from [Build Your First Letta Agent](/tutorials/letta-build-your-first-agent). The server now listens at `http://localhost:8283`, which is what `LETTA_BASE_URL` in your `.env` points to.

Install the Python dependencies for the driver. Create `requirements.txt`:

```text
letta-client
pyyaml
python-dotenv
```

Then install (a virtual environment is recommended):

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

## Step 7 — Write the Agent's Decision Tools

The agent doesn't touch the network. Instead it calls one of a few **decision tools** that simply *record* what it wants to do. Because these functions only return strings, they run safely in Letta's sandbox with no dependencies and no secrets.

Create `tools/decisions.py`:

```python
# tools/decisions.py
def draft_reply(reply_text: str) -> str:
    """Queue a reply to the Bluesky mention currently under review.

    Call this when a mention deserves a response. `reply_text` is the complete
    reply, written in the brand voice and kept to 300 characters or fewer (the
    Bluesky limit). The local manager posts it. Returns a confirmation string.
    """
    return f"QUEUED_REPLY: {reply_text}"


def skip(reason: str) -> str:
    """Skip the mention currently under review without replying.

    Call this for spam, off-topic noise, or anything that does not need a
    response. `reason` is a short explanation. Returns a confirmation string.
    """
    return f"SKIPPED: {reason}"


def draft_post(post_text: str) -> str:
    """Queue an original top-level post for Bluesky.

    Call this when asked to publish original content. `post_text` must be 300
    characters or fewer and match the brand voice. Returns a confirmation string.
    """
    return f"QUEUED_POST: {post_text}"


def compose_digest(title: str, body_markdown: str) -> str:
    """Queue a long-form article for Leaflet.

    Call this for content too long for a 300-character post — daily digests,
    essays, announcements. `title` is the headline; `body_markdown` is the full
    article in Markdown. Returns a confirmation string.
    """
    return f"QUEUED_DIGEST: {title}"
```

The docstrings matter: Letta turns each one into the tool's schema and uses it to decide *when* to call the tool. Spell out the constraints (the 300-character limit, what counts as "skip") right there in the docstring.

## Step 8 — Register the Tools and Create the Agent

Now the one-time setup. This script registers the four decision tools and creates an agent whose **memory blocks** encode its job, its brand voice, and who it's talking to. Those blocks persist on the server, so the voice stays consistent across every run.

Create `create_agent.py`:

```python
# create_agent.py
import os
from dotenv import load_dotenv
from letta_client import Letta

import tools.decisions as decisions

load_dotenv()
client = Letta(base_url=os.environ.get("LETTA_BASE_URL", "http://localhost:8283"))

# Register each decision tool. They use only the standard library, so no
# pip_requirements are needed.
tool_names = []
for fn in (decisions.draft_reply, decisions.skip,
           decisions.draft_post, decisions.compose_digest):
    tool = client.tools.create_from_function(func=fn)
    tool_names.append(tool.name)
    print("Registered tool:", tool.name)

agent = client.agents.create(
    model="openai/gpt-4o-mini",
    embedding="openai/text-embedding-3-small",
    tools=tool_names,
    include_base_tools=True,  # keep Letta's memory tools so the voice can evolve
    memory_blocks=[
        {
            "label": "persona",
            "value": (
                "I am the social media manager for Algo Dojo. I triage Bluesky "
                "mentions, reply when it adds value, and publish long-form digests "
                "to Leaflet. I act through my decision tools — I never claim to "
                "have posted something myself."
            ),
            "limit": 5000,
        },
        {
            "label": "brand_voice",
            "value": (
                "Voice: practical, friendly, expert but approachable. No hype, no "
                "emoji spam, no hard selling. Replies are short and genuinely "
                "useful. Topics stay on AI agents, ML, and workflow automation. "
                "Never make promises about pricing, timelines, or unreleased features."
            ),
            "limit": 5000,
        },
        {
            "label": "audience",
            "value": (
                "Our audience is developers and technical leaders evaluating "
                "agentic AI for real business workflows."
            ),
            "limit": 5000,
        },
    ],
)

print("\nAgent ID:", agent.id)
print("Add this to your .env as MANAGER_AGENT_ID")
```

Run it once:

```bash
python create_agent.py
```

Copy the printed agent ID into your `.env`:

```text
MANAGER_AGENT_ID=agent-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

## Step 9 — Write the Driver

The driver is the part that runs on a schedule. It has three modes:

- `engage` — pull mentions, ask the agent about each, post its replies.
- `post` — ask the agent for one original post and publish it.
- `publish` — ask the agent for a long-form digest and send it to Leaflet.

The shared trick is reading the agent's **tool calls** out of the response. When the agent calls `draft_reply(...)`, Letta returns a `tool_call_message` whose `tool_call.arguments` is a JSON string with the values the agent chose. We parse that and act on it locally.

Create `manager.py`:

```python
# manager.py
import json
import os
import subprocess
import sys
from datetime import date
from pathlib import Path

import yaml
from dotenv import load_dotenv
from letta_client import Letta

load_dotenv()
AGENT_ID = os.environ["MANAGER_AGENT_ID"]
client = Letta(base_url=os.environ.get("LETTA_BASE_URL", "http://localhost:8283"))

STATE_DIR = Path("state")
HANDLED_FILE = STATE_DIR / "handled.json"


def sh(args: list[str]) -> str:
    """Run a social-cli command and return its stdout (raising on failure)."""
    result = subprocess.run(args, capture_output=True, text=True)
    if result.returncode != 0:
        raise RuntimeError(f"{' '.join(args)} failed:\n{result.stderr}")
    return result.stdout.strip()


def ask(prompt: str) -> list[tuple[str, dict]]:
    """Send one prompt to the agent and return its (tool_name, args) calls."""
    response = client.agents.messages.create(
        agent_id=AGENT_ID,
        messages=[{"role": "user", "content": prompt}],
    )
    calls = []
    for message in response.messages:
        if message.message_type == "tool_call_message":
            args = json.loads(message.tool_call.arguments)
            calls.append((message.tool_call.name, args))
    return calls


def load_handled() -> set[str]:
    if HANDLED_FILE.exists():
        return set(json.loads(HANDLED_FILE.read_text()))
    return set()


def save_handled(handled: set[str]) -> None:
    HANDLED_FILE.write_text(json.dumps(sorted(handled)))


def engage() -> None:
    """Pull Bluesky mentions and let the agent decide how to respond to each."""
    sh(["social-cli", "sync", "-p", "bsky"])
    inbox = STATE_DIR / "inbox-bsky.yaml"
    data = yaml.safe_load(inbox.read_text()) if inbox.exists() else {}
    notifications = (data or {}).get("notifications", [])

    handled = load_handled()
    for note in notifications:
        # Field names can vary slightly by social-cli version — inspect
        # state/inbox-bsky.yaml once and adjust these .get() keys if needed.
        uri = note.get("uri") or note.get("id")
        text = note.get("text", "")
        author = note.get("author")
        handle = author.get("handle") if isinstance(author, dict) else note.get("handle", "someone")
        if not uri or uri in handled:
            continue

        prompt = (
            f'A Bluesky user @{handle} mentioned us: "{text}"\n\n'
            "Decide how to handle it. If it deserves a reply, call draft_reply "
            "with the reply text (max 300 characters, brand voice). If it does "
            "not, call skip with a short reason."
        )
        for name, args in ask(prompt):
            if name == "draft_reply":
                sh(["social-cli", "reply", args["reply_text"], "--id", uri, "-p", "bsky"])
                print(f"Replied to @{handle}")
            elif name == "skip":
                print(f"Skipped @{handle}: {args.get('reason', '')}")
        handled.add(uri)

    save_handled(handled)


def post() -> None:
    """Ask the agent for one original post and publish it to Bluesky."""
    prompt = (
        "Write one original Bluesky post (max 300 characters, brand voice) that "
        "shares a concrete, useful tip about building AI agents. Call draft_post "
        "with the text."
    )
    for name, args in ask(prompt):
        if name == "draft_post":
            sh(["social-cli", "post", args["post_text"], "-p", "bsky"])
            print("Posted:", args["post_text"])


def publish() -> None:
    """Ask the agent for a long-form digest and publish it to Leaflet."""
    prompt = (
        "Write today's Algo Dojo digest for Leaflet: 3-5 short paragraphs in "
        "Markdown explaining one practical idea about agentic AI or workflow "
        "automation. Call compose_digest with a title and the Markdown body."
    )
    for name, args in ask(prompt):
        if name == "compose_digest":
            title, body = args["title"], args["body_markdown"]
            archive = Path("content/digests") / f"{date.today()}-{_slug(title)}.md"
            archive.write_text(f"# {title}\n\n{body}\n")
            sh(["social-cli", "publish", "--title", title, "--content", body])
            print("Published to Leaflet:", title)


def _slug(text: str) -> str:
    return "".join(c if c.isalnum() else "-" for c in text.lower()).strip("-")[:50]


if __name__ == "__main__":
    mode = sys.argv[1] if len(sys.argv) > 1 else "engage"
    {"engage": engage, "post": post, "publish": publish}[mode]()
```

A few things worth calling out:

- **Deduplication is ours to handle.** Because we act with quick `reply`/`post` commands instead of `social-cli dispatch`, the CLI doesn't track what we've answered. The `handled.json` file does that, so a mention never gets two replies.
- **Inspect the inbox once.** Run `cat state/inbox-bsky.yaml` after your first `sync` and confirm the field names (`uri`, `text`, `author`) match what the driver reads. Adjust the `.get()` keys if your version differs.

## Step 10 — Run It

With the Letta server up and `.env` filled in, try each mode by hand first:

```bash
python manager.py engage     # triage + reply to current mentions
python manager.py post       # publish one original Bluesky post
python manager.py publish    # write + publish a Leaflet digest
```

Watch the output. On `engage`, you'll see one line per mention — either "Replied to @handle" or "Skipped". Check Bluesky to confirm the replies read the way you want. If the tone is off, you don't touch the code — you edit the `brand_voice` memory block (in the Letta UI at `app.letta.com`, or by re-running an updated `create_agent.py` for a fresh agent) and the change applies everywhere.

## Step 11 — Put It on a Schedule

The whole point is autopilot. A pair of cron jobs turns the driver into a always-on manager. Use absolute paths and your virtual environment's Python:

```text
# crontab -e   (adjust paths to your project + venv)

# Triage and reply to mentions every 15 minutes
*/15 * * * * cd /home/you/social-manager && .venv/bin/python manager.py engage >> manager.log 2>&1

# Publish a long-form digest to Leaflet every morning at 9am
0 9 * * * cd /home/you/social-manager && .venv/bin/python manager.py publish >> manager.log 2>&1

# Share one original post at noon
0 12 * * * cd /home/you/social-manager && .venv/bin/python manager.py post >> manager.log 2>&1
```

Because every cron run talks to the *same* Letta agent, the manager keeps a single, evolving memory of your brand across days and restarts — the same persistence you first saw in [Build Your First Letta Agent](/tutorials/letta-build-your-first-agent), now driving a live social account.

## Where to Go Next

You have a working autopilot, but there's plenty of room to grow it:

- **Add a human-in-the-loop gate.** Before the driver posts a reply, send the draft to yourself on [Telegram](/tutorials/letta-telegram-bot) and only publish on your approval — the safest way to run this against a real brand.
- **Use the native outbox loop.** For higher volume, write the agent's decisions to `outbox-bsky.yaml` and run `social-cli dispatch`, which handles deduplication and archiving for you.
- **Expand the surface.** `social-cli` also drives X, Semble collections, and margin annotations — add tools and modes for those the same way you added Bluesky and Leaflet.
- **Give the agent memory of who it talks to.** Add an archival-memory step so it remembers recurring community members and references past conversations in its replies.

The pattern underneath all of this is the one worth keeping: a stateful agent supplies the judgment and the consistent voice, a thin local driver supplies the hands, and a CLI does the platform-specific work. Swap the platform, keep the brain.
