## What You'll Build

Most "automate with LLMs" advice stops at *"add a review step and some guardrails."* That's not a skill — it's a slogan. This tutorial teaches the part that actually makes an automation trustworthy: **measuring it**.

You'll build a support-ticket **triage** workflow — the kind of repetitive, text-heavy task LLMs are great at — and by the end you'll be able to:

- Turn an LLM into a reliable **classifier** using structured output (no fragile string parsing)
- **Measure its accuracy** against a labeled test set, so "it seems to work" becomes "92% on 50 tickets"
- Use **confidence gating** to auto-resolve the easy cases and escalate the rest to a human — and quantify exactly how much work that saves

The skill is transferable: this build-then-measure loop applies to any LLM automation — email routing, document extraction, content moderation.

## The Workflow

When a support ticket arrives, someone reads it and decides three things: what it's *about* (category), how *urgent* it is (priority), and a short *summary* for the queue. We'll automate that decision and route on it.

```text
ticket → LLM triage → { category, priority, summary, confidence } → route
                                                          │
                                  high confidence ───────►├─ auto-route to the right queue
                                  low confidence ────────►└─ escalate to a human
```

## Step 1: Model the Output

The single biggest reliability win is **not** parsing free-form text. Define the exact shape you want with Pydantic, and the model is constrained to return it.

```python
# triage.py
from enum import Enum
from pydantic import BaseModel, Field

class Category(str, Enum):
    billing = "billing"
    technical = "technical"
    account = "account"
    other = "other"

class Triage(BaseModel):
    category: Category = Field(description="The single best-fit category for the ticket.")
    priority: int = Field(description="Urgency from 1 (low) to 5 (critical).")
    summary: str = Field(description="A one-sentence summary of the customer's issue.")
    confidence: float = Field(description="Confidence in the category, from 0.0 to 1.0.")
```

The `Category` enum is what makes this a *classifier*: the model can only return one of four known values, so downstream routing code never has to guess.

## Step 2: Write the Triage Function

`client.chat.completions.parse` returns your Pydantic object directly via `message.parsed`.

```python
# triage.py
from openai import OpenAI

client = OpenAI()

SYSTEM_PROMPT = """You triage customer support tickets. Classify each into exactly one category:
- billing: payments, invoices, refunds, charges, plans, pricing
- technical: bugs, errors, crashes, things not working
- account: login, profile, email/password changes, account deletion
- other: feedback, feature requests, anything that fits none of the above
Set priority by urgency and business impact. Report an honest confidence."""

def triage(ticket: str) -> Triage:
    completion = client.chat.completions.parse(
        model="gpt-4o-2024-08-06",
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": ticket},
        ],
        response_format=Triage,
    )
    return completion.choices[0].message.parsed
```

Try it:

```python
# triage.py
result = triage("I was charged twice for my subscription this month.")
print(result.category, result.priority, result.confidence)
# Category.billing 4 0.97
```

You now have a working automation. But "it worked on one ticket" is not a number you can stake a process on. Let's fix that.

## Step 3: Measure It (the actual skill)

You can't improve — or trust — what you don't measure. Build a small **labeled eval set**: real-ish inputs paired with the correct answer. Ten examples is enough to start; aim for 30–50 before you rely on the numbers.

```python
# triage.py
EVAL_SET = [
    ("I was charged twice for my subscription this month.", Category.billing),
    ("The app crashes every time I upload a CSV.",          Category.technical),
    ("How do I change the email address on my account?",    Category.account),
    ("Your product is amazing — just wanted to say thanks!",Category.other),
    ("I need a refund for the duplicate payment.",          Category.billing),
    ("Login returns a 500 error after the latest update.",  Category.technical),
    ("Please delete my account and all of my data.",        Category.account),
    ("I upgraded my plan but the invoice shows the wrong amount.", Category.billing),
    ("The dashboard charts won't load in Safari.",          Category.technical),
    ("Can you add a dark mode option?",                     Category.other),
]

def evaluate() -> float:
    correct = 0
    for ticket, expected in EVAL_SET:
        result = triage(ticket)
        hit = result.category == expected
        correct += hit
        print(f"{'✓' if hit else '✗'} got={result.category.value:9} exp={expected.value:9} "
              f"conf={result.confidence:.2f}  {ticket[:45]}")
    accuracy = correct / len(EVAL_SET)
    print(f"\nAccuracy: {correct}/{len(EVAL_SET)} = {accuracy:.0%}")
    return accuracy

evaluate()
```

Now you have a **scoreboard**. A typical run looks like:

```text
✓ got=billing   exp=billing   conf=0.97  I was charged twice for my subscription thi
✓ got=technical exp=technical conf=0.95  The app crashes every time I upload a CSV.
✗ got=billing   exp=other     conf=0.61  Can you add a dark mode option?
...
Accuracy: 9/10 = 90%
```

This single number changes how you work: tweak the prompt, add an example, switch models — and *rerun*. You're no longer guessing whether a change helped; you can see it. (Notice the miss came with low confidence — that's the lever for the next step.)

## Step 4: Confidence Gating — Automate Safely

90% accuracy isn't good enough to act on blindly. But look again: the model was **confident** when it was right and **unsure** when it was wrong. So don't auto-act on the unsure ones — escalate them. That's confidence gating.

```python
# triage.py
def measure_gate(threshold: float) -> None:
    auto = auto_correct = escalated = 0
    for ticket, expected in EVAL_SET:
        result = triage(ticket)
        if result.confidence >= threshold:
            auto += 1
            auto_correct += (result.category == expected)
        else:
            escalated += 1
    coverage = auto / len(EVAL_SET)
    auto_acc = (auto_correct / auto) if auto else 0.0
    print(f"threshold={threshold:.2f}  auto-handled={coverage:>4.0%}  "
          f"accuracy-on-auto={auto_acc:>4.0%}  escalated={escalated}")

for t in (0.00, 0.70, 0.80, 0.90):
    measure_gate(t)
```

A representative result:

```text
threshold=0.00  auto-handled=100%  accuracy-on-auto= 90%  escalated=0
threshold=0.70  auto-handled= 90%  accuracy-on-auto= 96%  escalated=1
threshold=0.80  auto-handled= 80%  accuracy-on-auto=100%  escalated=2
threshold=0.90  auto-handled= 70%  accuracy-on-auto=100%  escalated=3
```

This table *is* the engineering decision, made with data instead of vibes: raise the threshold to buy accuracy on the automated slice, at the cost of escalating more to humans. Pick the point that matches your tolerance — e.g. *"auto-handle anything ≥ 0.80, where we hit 100% on this set; a human reviews the other 20%."*

## Putting a Number on the Value

Now translate accuracy into hours. Suppose your team triages **200 tickets/day** and manual reading + routing averages **3 minutes** each:

```text
Manual baseline:  200 × 3 min            = 600 min/day  (10.0 hrs)
Gate at 0.80:     auto-handle 80%, human reviews the rest
  - 160 auto-routed:  ~0 min triage      =   0 min
  - 40 escalated:     40 × 3 min         = 120 min
Automated total:                         = 120 min/day  ( 2.0 hrs)

Saved: ~8 hours/day of routing — and the 80% auto-handled hit 100% on our test set.
```

Plug in your own volume and time-per-ticket. The point is that you can now **defend the automation with numbers**, which is exactly what gets it approved and shipped.

## Make It Reliable

A few cheap additions turn the prototype into something dependable:

```python
# triage.py
def triage_safe(ticket: str) -> Triage:
    result = triage(ticket)

    # Deterministic guardrail: some words must never be misrouted, no matter what.
    text = ticket.lower()
    if any(w in text for w in ("refund", "charged", "invoice")):
        result.category = Category.billing

    # Validate the model stayed in range (Structured Outputs won't enforce numeric bounds).
    result.priority = max(1, min(5, result.priority))
    return result
```

Round it out with:

- **Retries** — wrap the API call in a try/except and retry once on transient errors.
- **Logging** — record every `(ticket, result)` so your eval set keeps growing from real traffic.
- **Re-measure on a schedule** — models and ticket patterns drift; rerun `evaluate()` weekly.

## Common Pitfalls

| Mistake | Why it hurts | Fix |
|---|---|---|
| Parsing free-form text | Brittle; breaks on phrasing changes | Use structured output with a Pydantic schema |
| Open-ended category field | Downstream routing can't rely on the value | Constrain with a `Category` enum |
| Shipping without an eval set | "Seems fine" until it silently regresses | Measure accuracy on labeled examples first |
| Auto-acting on every prediction | Confident *and* unsure cases treated alike | Gate on `confidence`; escalate the rest |
| Numeric `Field(ge=…, le=…)` constraints | Strict Structured Outputs rejects `minimum`/`maximum` | Describe ranges in the prompt; clamp in code |
